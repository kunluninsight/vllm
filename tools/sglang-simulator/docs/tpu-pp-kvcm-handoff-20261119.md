# TPU PP KVCM compatibility handoff

Baseline: personal Aone branch `codex/vllm-qwen38-pp-20261116`, `4115211`.
Runtime source remains the calibrated `d17d65a` plus the fixes in this commit.
Delivery: `kunluninsight/vllm`, branch `qwen3.8-max-tpu-pp-dev`, using the same
source tree and history; GitHub main is not the base.

## Changes

- Port `zhuzi-z/sglang` commit `2fddf18`: install the Tair KVCM transfer hook
  even when the daemon imported the transfer class before bootstrap; make
  repeated installation idempotent.
- Adapt `171891f` to our existing metrics hook: serialize nested dataclass KV
  statistics as native IPC does, without registering another metrics wrapper.
- The earlier KVCM support and AsyncLLM connector registration already exist.
  Keep native control-plane lookup, allocation, publication and reclaim;
  simulate payload I/O only.

PP scheduling, native prompt truncation, scheduler metadata timing, max-PCP
models, barrier/communication configuration and zero model offsets are retained.
This does not reintroduce the colleague branch's old handoff compensation or
replace our bootstrap/collector implementation.

## Build and deployment

Build from this branch with the existing project Python environment:

```sh
cd tools/sglang-simulator
python -m pip wheel --no-deps --no-build-isolation . --wheel-dir dist
```

Install the resulting wheel into the existing compatible TPU/DashLLM runtime;
do not replace that runtime with GitHub vLLM main. Retain the four calibrated
max-PCP model files and the existing predictor configuration. Model weights
are separate deployment artifacts, not regenerated by this patch.

The simulation Python processes, including the V6D daemon, must inherit
`SGLANG_SIMULATOR_ENABLE=1` and `SIM_COLLECTOR_ENABLE=0`. For KVCM transfer mode,
retain native `DS_LLM_LAUNCH_V6D=1` and
`V6D_KVCM_MODE=report-event-and-cache-transfer`, plus the manager/tracker
configuration from the intended deployment. Use a separate simulation cache
namespace/instance group: payload transfers are simulated, so publishing into
the real service's cache would be invalid.

On startup, verify the `C_TairKVCMTransferRuntimeHook installed` log in the
daemon. Exercise cache miss, store then hit, asynchronous completion and metrics
reporting. Confirm there is no native MemPool payload client initialization and
no nested-stat exception. Validate KVCM event/query behavior and hit latency
against the real deployment before claiming cache accuracy.
